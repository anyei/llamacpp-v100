## 2. Item 3 - a CJK-aware draft vocabulary

Finding (vocabulary of the MTP head file, 248,320 ids, byte-level BPE `qwen35`): the ids are laid out in script blocks.
The first ~92k ids are almost all ASCII (English, code); **no Han (Chinese) token has an id below 95,726** - the 55,328
Han tokens sit at 95.7k-151.6k (median 123.7k) - and kana, hangul, Cyrillic and other scripts come after 151.6k. That is
why the first-N head of 8.2 collapsed Chinese acceptance: any N below ~96k removes every Chinese token, and the drafts
fall back to byte pieces.

Design: a subset = per-script quotas taken in id order (BPE merge order ~ frequency inside a script block) plus every
special, byte-piece and punctuation token; sized from a coverage measurement on the target's own outputs (a corpus
generated by Flash-Next: English, code, Chinese, Japanese, Korean, other European languages). Coverage bounds the
acceptance loss: a target token outside the subset can never be drafted. Implementation sketch (details after the code
study): at load, gather the subset's rows of the head's `output.weight` into a new tensor on the head's device; in the
draft graph, logits = that tensor x h, scattered into a full-width row pre-filled with -inf, so the host side (logits
copy, sampling, the p-min gate) is unchanged. Expected: <= ~2 ms per step (the head is 675 MB read 3x per step), minus
the extra VRAM (~2.7 MB per 1k ids) the cache gives up.
Stop rule: net < 1 ms per step, or acceptance on any prompt set drops by more than the time saved -> close.

## 3. Item 1 - stable CUDA graphs

Code study (2026-10-01, official tree at 1300d2bef; the earlier "KV views grow every token" reading was wrong):
- n_kv is already padded to 256 cells (`llama-kv-cache.cpp` get_n_kv; qwen4exp passes n_pad 1, the floor is 256) and
  the indexer cache tracks the same cells, so a shape can change only every 256 tokens. KV and indexer writes are
  SET_ROWS with index inputs, the doorbell's op params are fixed at create and its step is a graph input: nothing
  else in the decode graph changes per step.
- **The real cause: the qwen4exp decode graph is rebuilt on every step.** Two of its inputs - `llm_graph_input_qsa`
  (one per QSA layer) and `llm_graph_input_ple` - do not implement `can_reuse`; the base class returns false, so
  `llm_graph_result::can_reuse` always fails. Every step then rebuilds the ~4,400-node graph, re-splits it (new
  split uid, so ggml-cuda never takes its uid fast path and compares every node, ~1 KB each, ~4.5 MB per step with
  graphs on), and the build lands in the least-recently-used of the 4 decode-cache entries (4 rotating CUDA graph
  keys). At every 256-cell boundary each entry's compute buffer is re-planned or reallocated, so its addresses move.
- CUDA-graph eligibility is not the problem: the 1-row draft and 4-row verify graphs pass ggml-cuda's checks on V100.

Design (smallest first; each step measured before the next):
1. `can_reuse` for the QSA input (re-point mctx; check k_idxs = n_tokens, cell_blk = n_kv x n_stream, blk_cells,
   blk_pos and bias sizes) and the PLE input (re-point the attention context; rows = ple_n_heads x n_tokens).
   No runtime cost; removes the per-step build/split/alloc even with graphs off; with graphs on the uid stays and
   the graph replays. Gate: greedy texts identical (reuse changes no math); `LLAMA_GRAPH_REUSE_DISABLE=1` is the
   same-binary off switch; `LLAMA_DECODE_TIMING` shows the reuse count and the host phases.
2. If graphs still re-capture at the 256-cell boundaries: reserve the decode-cache schedulers at the maximum n_kv
   (buffers stop moving, `cudaGraphExecUpdate` handles the shape change) and/or a coarser n_kv pad behind an env
   (~50-80 ns per padded cell per step: pad 1024 ~0.04 ms/step).
3. `LLAMA_DECODE_GRAPH_CACHE` 6-8 if the draft (1 row) and verify (4 rows) widths keep evicting each other.
Expected: up to ~3 ms per step from replay (strata-port-plan 8.3) plus whatever the per-step rebuild costs today.

## 4. Item 2 - gather-based QSA attention

Code study (2026-10-01):
- Shapes: 24 Q heads, 2 KV heads (GQA 12), head dim 256; the selection is `min(n_kv, 2048 + 4 - 1)` = 2051 cells per
  query token, shared by all heads. Attention runs `ggml_flash_attn_ext` over the FULL cache views with an F16 mask
  (fill -inf, set_rows zeros at the top-k cells, plus the kq mask); on the V100 that is the Volta small-width kernel
  (T3), which at width 4 splits the 12 heads into 2 groups and so reads each KV head twice. **No FA kernel skips
  masked KV positions** at decode widths (KV_max trims only trailing all-masked tiles, and only for >= 1024 query rows).
- **The indexer costs more than the attention.** Every step and every QSA layer it re-pools ALL raw indexer keys:
  get_rows of n_kv raw keys to F32, mean of 4 per block (4 strided conts + 3 adds), RMS norm, MRoPE, then scores,
  the per-cell expansion and a full argsort of n_kv scores per query row (the CUB top-k path needs CCCL >= 3.2;
  the CUDA 12.8 image has 2.x). Roughly 120 MiB of traffic per layer at 32k - about twice the attention read - and
  all of it grows with the context.
- A graph-level gather (get_rows of the selected cells, then FA) pays at width 1 and at 262k, but at the production
  width-4 verify and 32k it is about break-even (per-row gathers read 4 x 2051 rows, and get_rows writes F32).
  The fork's only real gather (MiniMax-M3) handles single-token decode and falls back to a mask for batches.

Plan (measure first, exact changes before semantic ones):
1. Measure the context-dependent cost per step at ~30k and ~128k depth: today vs an ablation that skips the indexer
   (timing only), so the step splits into attention vs indexer.
2. Exact kernel skip in `fattn-mma-volta-small.cuh` behind `GGML_CUDA_FA_SKIP_MASKED`: a K/V row that every query row
   of the CTA masks is not loaded (and a fully masked 128-position step is skipped). Skipped terms are exact zeros,
   so the gate is byte identity; the 4 verify rows share the CTA and read the union of their selections.
3. The indexer: cache or fuse the pooled block keys (a complete block's pooled, normed, roped key never changes), and
   top-k over block scores (n_kv/4 keys). Caching must survive sequence removal and context shift; the block-level
   top-k changes the selection at the cutoff (the reference's whole-block rule) - a semantic choice for the user.

### 5.4 Item 2 - QSA at depth: the masked-position skip built (exact by design); depth costs ~22 ms per step at 29k

Built in the worktree (bins-fu5/fu7): in `fattn-mma-volta-small.cuh`, every lane checks whether any query row of the
block sees its position; masked rows feed zeros into the (warp-collective) mma instead of loading K and V, and a
128-position step with no visible position is skipped (exact: the running max, the sums and the output do not move).
Template flag + `GGML_CUDA_FA_SKIP_MASKED` (default on, `=0` restores the dense read). Gates: FLASH_ATTN_EXT oracle
3924/3924 (CUDA0 vs CPU, skip on); `-c 8192` QSA run (cache off) skip on vs off: mean KLD 0.000000, max 0.000056, same
top 100 %, PPL ratio 1.000115 +- 0.000115 - and two skip-OFF runs give exactly the same 1.000115 (`skip-det.sh`), so that
ratio is an artifact of the comparison on this one-chunk setup: **the skip is exact**.

Depth (reuse + CUDA graphs, production config otherwise, `depth-run2.sh`, prompt dec7 = 28,357 tokens):

| | short prompt (dec1) | 28k-token prompt (dec7) |
|---|---|---|
| ms per MTP step, skip off (two runs) | 57.1 / 56.8 | 79.4 / 78.7 |
| ms per MTP step, skip on (two runs) | 57.1 / 57.4 | 77.5 / 78.1 (-1.6 %) |
| prefill (t/s) | - | 317 / 318 |

At ~95k (dec8 = 94,624 tokens, `-c 131072`, cache 10000 MiB to fit the KV, `-ub/-b 1024`; prefill 105 t/s): skip off
126.1 ms per MTP step, skip on 123.8 (-1.8 %), identical acceptance (162/277).

**Depth adds ~22 ms per step at 28k, and the attention read is only ~2 ms of it.** Code reading found a host-side
cost that grows with the context: every QSA layer's input (`set_input_qsa`) walks all n_kv cells and all blocks on the
host before the step can launch - 12 identical passes per step (the maps depend on the cache layout, the ratio and the
bias mode only). bins-fu8 shares one QSA input across the layers (exact; `share-run.sh` measures it). The GPU-side
indexer cost comes from the per-op profiles.

GPU side of the indexer, first exact step (bins-fu9): the block mean was a get_rows to F32 plus 4 strided conts, 3 adds
and a scale (~70 MB of traffic per QSA layer at 28.7k cells); for a power-of-two ratio (Flash-Next: 4) it is now one
`ggml_pool_2d` average over the r member rows of each block. The CUDA pool adds the members in the same order and
scales each by 1/r first, which is exact for a power of two, so the values match (gate: KLD 0 vs fu8, `pool-run.sh`).
Expected ~0.7 ms per step at 28k, ~2.5 ms at 100k. Still open on the GPU: the 12 full argsorts of n_kv scores per
step (~0.18 ms each at 29k on the profile) - a top-k over block scores would be 4x smaller but changes which cells are
taken at the cutoff when scores tie (ReLU sums tie at zero often): a semantic choice, the user's call.

Per-op GPU time at 28k (bins-fu7, `GGML_CUDA_OP_PROFILE`, graphs off, instrumented - absolute values are inflated by
the per-node events; ms per half-step graph, two GPU graphs per MTP step), skip off -> on: FLASH_ATTN_EXT 0.849 ->
0.613; unchanged by the skip: TOP_K 1.91, GET_ROWS 1.89, CONT 2.51, ADD 1.83, SCALE 0.99, SUM_ROWS 0.40, CPY 0.45
(most of these are the indexer chain and the mask build), MUL_MAT 7.2, MUL_MAT_ID 5.4, MOE_JOIN 4.0-4.5 (the GPU waiting
for the host executor). Reading: at 28k the GPU-side indexer is ~12 ms per MTP step - pooling traffic (fu9 removes most
of the CONT/ADD/SCALE part), the F32 gather of every raw key (GET_ROWS) and the 12 full argsorts (TOP_K) - against
~1.2 ms of attention after the skip. The skip cannot drop whole 128-position steps at 28k: four verify rows x 2051
selected cells in blocks of 4 touch most steps; it saves the K/V loads of the unselected rows only.

Shared QSA input (bins-fu8, `share-run.sh`): exact (fu8 vs fu7, cache off, `-c 8192`: KLD 0, same top 100 %, the same
constant 1.000115 ratio as the control). Host input time at 28k (`LLAMA_DECODE_TIMING`, graphs off, per 256 ubatches):
set_inputs 312.7 -> 134.4 ms (about 4.9 -> 2.1 ms per MTP step). Speed with reuse + graphs + skip, arms fu7 / fu8 / fu8 /
fu7: 28k prompt **78.9 / 78.4 -> 72.3 / 72.3 ms per MTP step (-8.1 %)**; short prompt 57.0 / 57.0 vs 56.6 / 57.0 (no
change, as expected).

Pooled indexer mean (bins-fu9, `pool-run.sh`): exact (fu9 vs fu8: KLD 0, same top 100 %, the control's constant ratio).
Speed at 28k (reuse + graphs + skip + shared input), arms fu8 / fu9 / fu9 / fu8: 72.4 / 72.1 / 71.3 / 72.9 ms per MTP step
-> fu9 **71.7 vs 72.65 (-1.3 %)**; short prompt unchanged (56.2-56.8). Small: most CONT/ADD/SCALE time in the profile
belongs to other parts of the graph.

### 8.4 7.4 first look: the decode-graph cache difference is systematic, from different kernel fusion

Probe `bench156/dgc-det.sh` (fu13 = with the 8.1 fix; Flash-Next, `-ub 4`, 2 x 2048 chunks, MoE cache off, graphs off):
main scheduler twice -> KLD 0; decode-graph cache on, two runs -> **KLD 0.014920 both times** (same top 97.556 %), i.e.
deterministic, not a race. The router runs unfused in both paths (SOFT_MAX / ARGSORT / GET_ROWS / SUM_ROWS / DIV), so
the topk-moe fusion is not the difference. The op profiles (`GGML_CUDA_OP_PROFILE=256`, logs `dgc-prof-{main,cache}.log`)
differ in which nodes launch as their own kernel: main shows ROPE `Qcur` / `node`, UNARY `gate_sigmoid` and a CONT
of the PLE conv weight; the cache path shows ROPE `indexer_q`, ADD `indexer_score_tokens` and a separate SET_ROWS -
the two schedulers hand the CUDA backend graphs that fuse differently (rope + KV write, the sigmoid gate, the indexer
bias add). Fused and unfused kernels round differently, and the QSA top-k turns tiny score differences into different
selected cells, which is why the KLD is far above the float-order level. Next (needs a pick): find why the node order /
split boundaries differ between the two schedulers and align them (cache path bit-identical to main), or document it as
a float-order + QSA-selection effect and keep the cache (it is faster: 56.4 vs 59.5 ms per MTP step).

**7.4 cause found (2026-10-01, user: "do the 7.4 the way you suggested" = make the cache path match the main path):**
`llama_context::graph_get_cb()` pins every weighted norm output (`norm-<il>`: attention q/k norms, indexer q/k norms,
the GDN output norm) and `l_last` to the layer's device for small batches (n_tokens < 32) - but it always pins into the
MAIN scheduler (`sched.get()`). Decode-cache graphs are built for a cache entry's own scheduler (`ggml_backend_sched_new`
per entry, #8), which never receives the pins; its assignment passes then place some neighbours differently (the op
profile shows ROPE `Qcur` and the GDN `gate_sigmoid` missing from the cache path's CUDA profile - they run on the CPU
there), so the graph splits and fuses differently and the numbers move. Fix (worktree, bins-fu15): a
`sched_build` member set to the scheduler being built for around `model.build_graph()` in `process_ubatch`, and
the callback pins into `sched_build ? sched_build : sched.get()`. Queued on the X99 after the 7.3 suite
(`bench156/dgc-fix.sh`): cache path vs main scheduler KLD (expect 0) twice, the unfixed bins for contrast, and the
production decode speed old vs new (interleaved).

## 9. 7.3 design: block-level top-k for the QSA indexer (opt-in; semantic)

**Today** (`build_qsa_top_k` + `build_attn_qsa`): `indexer_score` holds one value per block and query row; the per-block
bias is added (complete visible block 0, incomplete block -inf, every block from the query's tail start on +1e9); the
scores are expanded to all n_kv cells (`get_rows` by `cell_blk`), the attention mask is added per cell (this is what
drops the future blocks the +1e9 also reached), and `ggml_top_k` keeps `indexer_top_k + r - 1` cells - a full argsort of
n_kv keys per row on CCCL 2.x. `build_attn_qsa` then writes zeros at those cells into a -inf mask (`set_rows`) and adds
the causal mask. Costs per QSA layer: the [n_kv, n_tps] expansion + mask add, and the n_kv-key sort (TOP_K ~3.8 ms per
MTP step at 28k for the 12 layers, linear in n_kv). Semantic quirks vs the reference (audit divergence 1): ties at the
cutoff can split a block (cells of equally scored blocks interleave in the sort; ReLU sums of exactly 0 tie often), and
the fixed width over-selects up to r - 1 cells of the next block when the tail has fewer than r - 1 visible cells.

**Design** (reference semantics: `block_topk = indexer_top_k / r` whole complete blocks + the true tail):
1. Block scores: `indexer_score` + a per-block bias for this mode: complete block wholly visible to the row (its last
   position <= q) 0, everything else -inf (incomplete blocks, the tail block, future blocks). Host cost n_blocks per
   row - the same pass as today's per-block bias, different values.
2. `ggml_top_k(scores, k_blk)` over n_blocks keys, k_blk = min(n_blocks, block_topk): a sort of n_kv / r keys (4x fewer
   at r = 4) and no [n_kv, n_tps] expansion.
3. Expand the selected blocks to cells: `blk_cells` viewed [r, n_blocks] gathered by the block ids -> [r*k_blk, n_tps]
   cell ids (complete blocks only, so every entry is a real cell).
4. The tail by index: a new host input `tail_idx` [r, n_tps, n_stream] (I32) with the row's visible tail cells
   (positions tail_start..q, 0..r-1 of them) and `tail_val` (F32: 0 for a real tail cell, -inf for padding).
   `build_attn_qsa` applies the tail first, the blocks second, into the -inf fill:
   `m = set_rows(fill(-inf), tail_val, tail_idx); m = set_rows(m, zeros, sel_cells); m = m + kq_mask` - padding writes
   -inf over -inf (no-op), and a selected cell's zero is written after any tail write, so duplicates cannot re-mask.
5. Gate: `LLAMA_QSA_BLOCK_TOPK=1` (value-parsed, default off); off = today's graph and inputs exactly. Only in the
   per-block-bias mode (causal, no alibi, mask shape matches); otherwise the cell-level path runs.

**Edges to handle in the implementation:** fewer complete visible blocks than k_blk (short context: today and this
both end up dense; the -inf blocks the sort still returns must not expand to cell 0 - `blk_cells` of an incomplete
block holds 0 for missing members, so those slots need a masked sentinel or k_blk clamped per graph); multi-stream
(`blk_cells` row per stream, as today); the decode-graph cache / graph reuse (`can_reuse` must also check the new
input shapes); `r` not a power of two (the expansion does not care).

**Expected effect:** selection = the reference; vs today only at the cutoff. Speed estimate 2.5-3.5 ms per MTP step at
28k (sort 4x smaller, expansion gone), more at ~95k. **Measure before any default flip** (user rule): KLD vs today
(cache off, main scheduler) on wikitext at 8k / 32k / ~95k, the exact-answer probes, speed at 28k / ~95k, and the #143
transformers oracle if it covers QSA. Code goes to the worktree first; nothing in the official tree before the numbers.

**Implementation notes (2026-10-01, before coding; user go: "build it opt-in and show me the numbers"):**
- Bias in block mode, per query row q (tail_start = (q+1)/r*r): `0` if `b*r < tail_start` (the block lies wholly at or
  before q) and the block is complete (`filled[b] == r`), else `-inf`. The tail block and every future block are out of
  the ranking; the causal mask added at the end still guards every selected cell.
- `k_blk = min(n_blocks, indexer_top_k / r)` (512 at r = 4); `ggml_top_k` over the block scores.
- Expansion through a new input `blk_cells_x` (I32 [r*n_blocks, n_stream], the same map as `blk_cells` but a missing
  member reads `n_kv`), gathered by the winning block ids -> [r*k_blk, n_tps, 1, n_stream] cell ids.
- The tail through a new input `tail_idx` (I32 [r, n_tps, n_stream]): the cells of positions tail_start..q, padded
  with `n_kv`. Position p's cell is `blk_cells_x[p]` (the map is laid out by position).
- One spare mask column instead of ordered writes: the -inf fill is [1, n_kv + 1, n_batch, n_stream]; both `set_rows`
  (tail, then blocks) write zeros, every `n_kv` index lands in the spare column, and the view back to
  [n_kv, n_batch, 1, n_stream] drops it before the causal mask is added. Duplicates write the same zero.
- `cell_blk` is not built in block mode (nothing reads it); `can_reuse` checks the new shapes.
- Gate `LLAMA_QSA_BLOCK_TOPK` (value-parsed); block mode only where the per-block bias mode applies (causal, no
  alibi, mask shape matches). Off = today's graph exactly.
